## Goal

Tighten `parseRange` in `src/utils.ts` so that bad inputs throw clear, actionable errors instead of silently returning weird arrays. Add the corresponding tests.

## Acceptance Criteria

- [ ] `parseRange("")` throws `Error` whose message contains the word `empty`.
- [ ] `parseRange("5-3")` throws `Error` whose message contains the words `start` and `end` (it should explain that start must be ≤ end).
- [ ] `parseRange("a-b")` continues to throw an `Error` whose message contains `invalid` (existing behavior — don't regress).
- [ ] Existing happy-path behavior is unchanged: `parseRange("1-5")` still returns `[1,2,3,4,5]`, `parseRange("3-3")` still returns `[3]`.
- [ ] Add 3 new tests in `tests/utils.test.ts` — one per error case (`""`, `"5-3"`, `"a-b"`). Use `assert.throws` with a regex matcher on the message.
- [ ] `npm test` passes (all old tests + new ones).

## Constraints

- Modify only `src/utils.ts` and `tests/utils.test.ts`.
- Don't change `parseRange`'s signature.
- Keep TypeScript `strict` mode happy.

## Out of Scope

- Comma-separated ranges (`"1-3,5-7"`).
- Step values (`"1-10:2"`).
- Negative-number ranges.
